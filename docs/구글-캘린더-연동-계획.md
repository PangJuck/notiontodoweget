# 구글 캘린더 연동 — 무엇을 왜 그렇게 골랐나

**성준의 개인 할 일은 구글 캘린더 API로 직접 써넣는다.** 이건 다 붙었고,
설정 방법은 `worker/README.md`의 "구글 캘린더에 실제로 써넣기"에 있다.

처음에는 `.ics` 한 장을 내주고 구글이 구독하게 했는데(`worker/feed.js`, 코드는
남아 있다), **구글은 URL로 구독한 캘린더를 모바일 앱에 안 내려보낸다.** 아이폰에
띄우는 것이 목적이었으므로 그 길로는 끝까지 갈 수가 없어 API로 옮겼다.
**둘을 같이 켜면 같은 할 일이 두 번 보인다.**

지금 붙어 있는 것:

- `worker/connectors/calendar.js` — 서비스 계정으로 토큰을 받아 일정을
  쓰고 지운다. `CALENDAR` 시크릿이 없으면 아무 일도 하지 않는다
- `worker/index.js`의 네 곳에서 `syncTodo(env, ...)`를 부른다 — 할 일을 만들 때
  (마감일이 있으면), 마감일을 옮길 때, 완료할 때, 지울 때. 웹에서 한 일은 **바로**
  올라간다
- `worker/index.js`의 `scheduled` → `reconcile()` — 10분에 한 번. 클로드(MCP)와
  위젯은 노션에 **직접** 쓰고 워커를 지나가지 않으므로, 그 길로 들어온 것은
  여기서 잡는다. 바뀐 것을 기억해 두지 않고 매번 양쪽을 대조해 맞춘다
- `worker/test/worker.test.js` — 설정이 없으면 바깥으로 나가는 요청이 하나도
  없다는 것, **커넥터가 터져도 할 일은 저장된다**는 것, 토큰 JWT가 진짜로
  서명돼 있다는 것, 그리고 **팀원 항목이 성준 캘린더로 새지 않는다**는 것

아직 안 붙은 것은 팀원 캘린더에 쓰기, 회의실 잡기, 양방향이다. 아래는 그때
다시 꺼내 볼 판단들이다.

## 1. 인증을 어느 쪽으로 할지 — 이게 제일 큰 갈림길

"워커가 구글 캘린더에 쓸 자격"을 얻는 길은 셋이다.

| | A. 서비스 계정 + **캘린더 공유** | B. 서비스 계정 + 도메인 전체 위임 | C. 사람마다 OAuth 동의 |
|---|---|---|---|
| 필요한 권한 | 없음 | 회사 Workspace **관리자** | 없음 |
| 개인 gmail | **된다** | 안 된다 | 된다 |
| 사람이 하는 일 | 캘린더 하나를 공유 (2번 클릭) | 관리 콘솔 설정 | 브라우저에서 한 번 허용 |
| 워커가 쥐는 것 | 서비스 계정 키 하나 | 서비스 계정 키 하나 | 사람마다 refresh token |
| 새 저장소(KV) | 필요 없음 | 필요 없음 | **필요하다** |
| 닿는 범위 | **공유한 캘린더만** | 도메인 전원 | 동의한 사람 |
| 끊는 법 | 공유 해제 | 관리 콘솔 | 토큰 폐기 |

**성준 개인 캘린더 하나면 A다.** 노션 계정이 개인 gmail(`ghaos009@gmail.com`)이라
B는 아예 안 되고, C는 refresh token을 담을 KV가 필요해서 부품이 는다. A는
"서비스 계정도 사람처럼 캘린더를 공유받을 수 있다"는 것을 이용한다 — 구글
캘린더에서 그 서비스 계정 이메일에게 **일정 변경 권한**으로 공유하면 끝이다.

A로 간다면 사람이 해야 할 준비:

1. GCP 프로젝트에서 서비스 계정 만들기 → JSON 키 받기.
   Google Calendar API도 그 프로젝트에서 "사용 설정"해 둔다
2. 구글 캘린더에서 **할 일 전용 캘린더를 하나 새로 만든다**
   (예: `Ulick 할 일`). 본 캘린더에 바로 쓰지 않는 이유는 두 가지다 —
   키가 새도 피해가 그 캘린더 하나로 끝나고, 할 일과 진짜 약속이 안 섞인다
3. 그 캘린더 → 설정 → **특정 사용자와 공유** → 서비스 계정 이메일
   (`...@....iam.gserviceaccount.com`)을 **"일정 변경 권한"**으로 추가
4. 같은 설정 화면 아래 **캘린더 ID**를 복사한다 (`....@group.calendar.google.com`)
5. `npx wrangler secret put CALENDAR` 에 한 줄 JSON:
   ```json
   {"provider":"google","client_email":"...@....iam.gserviceaccount.com","private_key":"-----BEGIN PRIVATE KEY-----\n...","calendar_id":"....@group.calendar.google.com"}
   ```
   키 값은 시크릿으로만 들어간다. 저장소에도 이 문서에도 남기지 않는다

A에서 알아둘 제약:

- 토큰을 받을 때 `sub`(남의 자격으로 행세하기)를 쓰지 않는다. 서비스 계정
  **자기 자격**으로 공유받은 캘린더에 쓰는 것이다
- `calendarId`에 `primary`를 쓰면 안 된다. 그건 서비스 계정 자신의 캘린더다.
  반드시 4번에서 복사한 캘린더 ID를 쓴다
- 서비스 계정은 **참석자를 초대하지 못한다**(도메인 전체 위임이 없으면 초대
  메일을 못 보낸다). 혼자 보는 할 일 일정에는 상관없지만, 회의·회의실로
  넘어가면 그때는 B나 C가 필요하다

**.ics 구독과 둘 다 켜지 않는다.** 같은 할 일이 두 번 보인다. API로 갈아타면
구글 캘린더에서 구독하던 .ics를 빼거나, `ICS_TOKEN` 시크릿을 지운다.

## 2. 워커에서 구글 토큰을 받는 법

워커에는 `googleapis` 라이브러리가 없다. `fetch`로 직접 한다 — 어렵지 않다.

1. JWT를 만든다: `{iss: client_email, scope, aud:
   "https://oauth2.googleapis.com/token", exp, iat}`
   (A안에서는 `sub`를 넣지 않는다. B안으로 갈 때만 `sub`에 그 사람 이메일을 넣는다)
2. 서비스 계정 개인키로 RS256 서명한다. `crypto.subtle.importKey("pkcs8", ...)`
   + `crypto.subtle.sign("RSASSA-PKCS1-v1_5", ...)` — **워커에 이미 있는 것들이다**
   (같은 API를 `index.js`의 `verifyAccessJwt`가 검증 쪽으로 쓰고 있다)
3. `POST https://oauth2.googleapis.com/token` 에
   `grant_type=urn:ietf:params:oauth:grant-type:jwt-bearer&assertion=<JWT>`
4. 받은 `access_token`은 1시간짜리다. 워커가 살아 있는 동안만 메모리에 캐시한다
   (`accessKeys` 캐시와 같은 방식)

## 3. 할 일 하나가 이벤트 하나로

| 노션 | 구글 캘린더 |
|---|---|
| `할 일` | `summary` |
| `마감일` | `start.date` / `end.date` — **종일 이벤트**. 시간이 없으니 시간을 지어내지 않는다 |
| `메모` | `description` 에, 노션 페이지 링크와 함께 |
| `우선순위` | `colorId` (1~4를 색으로) |
| 담당자 | 그 사람 캘린더에 쓰는 것으로 대신한다. `attendees`를 쓰지 않는다 |
| page_id | 이벤트 `id`로 변환해 둔다 |

**이벤트 id를 노션 page_id에서 만들어 내는 것이 핵심이다.** 그래야 같은 할 일을
두 번 넣지 않고, 마감일을 옮길 때 새로 만들지 않고 고칠 수 있고, 매핑을 어디에
저장할 필요가 없다(= KV가 필요 없다). 구글 이벤트 id 규칙은 **소문자 a–v와
숫자 0–9, 5~1024자**다. page_id는 16진수(0-9a-f)라 하이픈만 빼면 그대로 들어간다:

```js
const eventId = "todo" + pageId.replace(/-/g, "");   // 32자 + 4 = 36자, 규칙 안
```

그러면 `upsert`는 `PUT .../events/{eventId}`(없으면 만들고 있으면 덮는다) 하나로
끝나고, `remove`는 `DELETE .../events/{eventId}` 하나다. 이미 없으면 404가 오는데,
그건 성공으로 친다.

## 4. 어느 캘린더에 쓸지 — 한 번 정하고 가야 한다

할 일은 그 사람 **개인 캘린더**에 쓴다. 팀 공용 캘린더에 몰아 쓰면, 지금은 팀
DB 안에서만 보이던 것이 회사 전체 일정에 뜨게 된다 — 보이는 범위가 슬그머니
넓어지는 쪽으로 가지 않는다.

성준의 **개인 DB**(업무가 아닌 것)는 캘린더에 보낼지 따로 정한다. 기본은 안
보내는 쪽을 권한다. 회사 계정 캘린더에 개인 일정이 섞이기 시작하면 되돌리기가
번거롭다.

## 5. 회의실 자동 예약 — 그 다음 단계

회의실은 Workspace의 **리소스 캘린더**다. 잡는 방법은 회의실을 참석자로 넣는
것이다.

```json
{ "summary": "3PL 견적 회의",
  "start": {"dateTime": "2026-09-20T14:00:00+09:00"},
  "end":   {"dateTime": "2026-09-20T15:00:00+09:00"},
  "attendees": [{"email": "회의실주소@resource.calendar.google.com", "resource": true},
                {"email": "동료@회사.com"}],
  "conferenceData": { "createRequest": { "requestId": "..." } } }
```

필요한 것:

- 관리 콘솔에서 **건물/리소스**로 회의실이 등록돼 있어야 한다
- 빈 회의실을 고르려면 `freebusy.query`로 후보 회의실들의 빈 시간을 먼저 묻는다
- 구글 미트 링크까지 만들려면 `conferenceDataVersion=1`을 붙인다

다만 이건 **할 일과 다른 물건이다.** 할 일에는 시작·끝 시간이 없고 회의에는
있다. 노션 DB에 시간과 참석자를 넣기 시작하면 할 일 관리가 일정 관리로 번진다.
회의는 따로 창구를 두는 쪽(예: MCP 도구 `book_meeting`)이 깔끔하다 — 팀원이
자기 Claude에게 "내일 오후에 창준님이랑 한 시간 잡아줘"라고 말하면 되는 그림이다.

## 6. 양방향은 마지막에

구글 쪽에서 날짜를 옮긴 것을 노션이 알게 하려면 푸시 알림(`events.watch`)을 받을
공개 엔드포인트와, 채널을 며칠마다 갱신하는 장치, 그리고 어느 쪽이 최신인지
가리는 규칙이 필요하다. **한 방향(노션 → 구글)부터 쓰고, 정말 필요해지면 그때
붙인다.** 한 방향만으로도 "내 할 일 마감일이 캘린더에 박힌다"는 목적은 이룬다.

## 붙이는 순서 제안

1. 마감일 → 종일 이벤트 (단방향). 위 3번만 하면 된다
2. 어느 캘린더에 쓸지 확정 (4번)
3. 회의 만들기 + 회의실 (5번). 창구를 따로 둔다
4. 양방향 (6번) — 정말 필요해지면
